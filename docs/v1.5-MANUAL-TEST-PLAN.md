# v1.5 Media Export — Manual Test Plan

Branch: `v1.5-media-export`. Run every section before accepting.
The offline gate (`node tests/run-tests.js`, 124 checks) must already be green
— it covers detection/rewriting/zip logic (incl. the ChatGPT `role:'tool'`
DALL-E generated-image path and Grok's inferred detection) but **cannot**
verify the live API field names or the auth contexts; that is what this plan
is for.

Legend: each step lists **Do** and **Expect**. Stop at the first hard
mismatch and file it against the step number.

## 0. Setup

1. **Do:** `git checkout v1.5-media-export` in a fresh clone/folder.
2. **Do:** Chrome → `chrome://extensions/` → Developer mode ON → *Load
   unpacked* → select the repo folder. If the extension was already loaded,
   click its **Reload** (circular arrow) — a manifest change (new host
   permission) requires it.
   **Expect:** extension loads with no errors; version shows **1.4.3**
   (deliberately not bumped); permission list includes the new
   `*.oaiusercontent.com` host.
3. **Do:** open the service-worker console: extension card → *Inspect views:
   service worker*. Keep it open for all tests (media warnings log there
   with the `[Exporter] media:` prefix).

## 1. Regression — exports WITHOUT images must be byte-identical

> This is the streak-critical check. Do it FIRST.

1. **Do:** open a text-only Claude conversation (no uploads, no pasted
   images) at `claude.ai/chat/...`. Click the extension icon → export `.md`.
   **Expect:** a single `.md` file downloads (NOT a zip), same filename
   pattern as v1.4.3 (`Claude_USER_ASSISTANT_<date>_<id8>.md`); status says
   `Exported N messages from Claude`; word count appears.
2. **Do (strong form):** run the same export with stock v1.4.3 (main branch
   loaded as a second unpacked copy or before/after switch) and
   `fc /b old.md new.md` (Windows) the two files.
   **Expect:** byte-identical.
3. **Do:** repeat step 1 for a text-only ChatGPT conversation, both `.md`
   and `.json`.
   **Expect:** single file, v1.4.3-identical content, no zip, no new status
   messages.
4. **Do:** export one Gemini and one Grok conversation.
   **Expect:** unchanged v1.4.3 behavior for text-only. Gemini has no media
   support (DOM scrape). Grok now has **inferred** generated-image detection:
   a text-only Grok conversation must still be byte-identical (no `media`,
   no placeholders); a Grok conversation with a generated image MAY now
   produce a zip/html with the image — but the field names are guessed, so
   if it produces nothing, check the SW console for `media: skipped` lines
   revealing the real response shape (see architecture notes, Grok section).
5. **Do:** check the service-worker console.
   **Expect:** NO `[Exporter] media:` lines for any of the above. If any
   appear for a "text-only" conversation, the detectors are over-matching —
   file it.

## 2. Claude conversation WITH images

1. **Do:** in Claude, open (or create) a conversation where you uploaded at
   least 2 images (e.g. paste a screenshot + upload a photo) and Claude
   replied. Ideally also attach one text file (.txt/.csv) somewhere in it.
2. **Do:** extension icon → `.md`.
   **Expect:** status progresses `Extracting… → Downloading N attachments… →
   Packing zip… → Exported N messages + K attachments from Claude`; ONE
   `.zip` downloads (no separate files).
3. **Do:** extract the zip.
   **Expect:** `<base>.md` at the root + `assets/` folder containing the
   images with sensible names (original filename if the API supplies one,
   else `image-N.png/jpg`); the text attachment appears as `assets/<name>.txt`
   containing the platform-extracted text.
4. **Do:** open `<base>.md` in a markdown viewer (VS Code preview is fine)
   from the extracted folder.
   **Expect:** images render inline via the relative `assets/...` links, in
   the right message positions; NO literal `asset:mN` strings anywhere
   (search the file for `](asset:` — must be zero hits).
5. **Do:** open each image from `assets/`.
   **Expect:** valid, full images. **Check specifically whether they are
   full-resolution or downscaled previews** — the Claude endpoint used
   (`.../files/{uuid}/preview`) is an inferred guess and may serve a resized
   copy. If downscaled: note it; the fix is swapping the URL field priority
   in `media-utils.js:firstUrlField` once the real field name is known
   (see the network tab for what claude.ai itself requests).
6. **Do:** export the same conversation as `.json`.
   **Expect:** one zip; message `text` fields contain `assets/...` links.
7. **Do (schema truth check):** in the service-worker console, run the
   conversation fetch manually or just re-export and watch for
   `[Exporter] media: skipped` warnings.
   **Expect:** none. Any warning shows a real field shape the detectors
   missed — copy it (it is truncated to 300 chars and content-free-ish, but
   still treat it as private) and update `media-utils.js` + fixtures.

## 3. ChatGPT conversation WITH images

> Everything ChatGPT-side is inferred; treat this section as schema
> discovery, not just verification.

1. **Do:** open a ChatGPT conversation where you uploaded an image AND one
   where ChatGPT generated an image (DALL-E/gpt-image) — generated ones use
   a different pointer scheme (`sediment://`).
2. **Do:** export `.md` from each.
   **Expect:** one zip each, `assets/` images valid, inline links render,
   no `](asset:` remnants, no failure notes — same criteria as section 2.
3. **Expect (naming):** the uploaded image should keep its original filename
   (recovered from `metadata.attachments`); generated images fall back to
   `image-N.<ext>` or the position-encoded `msgNNN-imgN.<ext>`.
4. **Do:** watch the page's own DevTools console (F12 on the ChatGPT tab)
   during export.
   **Expect:** no CORS errors surfacing as failed assets. (A CORS failure on
   the signed URL is handled by the service-worker fallback — the export
   should still succeed. If assets FAIL: check the SW console for
   `could not resolve download_url` — that means the `/backend-api/files/...`
   endpoint shape guess is wrong; capture the real endpoint from the network
   tab while ChatGPT itself displays an image.)

## 3b. [CRITICAL] ChatGPT ASSISTANT-GENERATED images — the 2026-07-08 bug

> This is the reason for the 2026-07-08 change. Real-browser finding
> (Zaina): in a ChatGPT image-generation window with images on BOTH sides,
> the export captured ONLY the user's uploads, NOT the assistant-generated
> images. The whole fix (walking `role:'tool'` DALL-E messages) is INFERRED
> — **this section is the only true confirmation.**

1. **Do:** open a ChatGPT conversation that has images on BOTH sides — you
   uploaded at least one image AND the assistant GENERATED at least one image
   (ask it to "generate/draw an image"). Export `.md` (or `.html`).
2. **Expect (the fix):** the export contains BOTH images — the upload AND the
   generated one — each at its correct position, inline. Before this fix only
   the upload came out. If the generated image is MISSING, the fix's core
   assumption (generated images live on a `role:'tool'` message with an
   `image_asset_pointer` part) is wrong for this account/model.
3. **If the generated image is missing — schema discovery:** open the raw
   backend-api response. In the ChatGPT tab DevTools → Network, find the
   `conversation/{id}` request and inspect its JSON `mapping`. Locate the node
   holding the generated image's `image_asset_pointer` (search the response
   for `asset_pointer`) and note that node's `message.author.role` and
   `.name`. If it is not `tool`, the walker's role check in
   `walkChatGPTTree` needs that role added. Report the finding — do NOT
   assume the tests passing means live works (the fixture shapes are guessed).
4. **Expect (positioning + naming):** the generated image reads on an
   assistant turn (not attributed to the user), and its filename is
   position-encoded (`msgNNN-imgN.ext`) or the recovered name — matchable to
   its spot in the conversation.
5. **Expect (no chatter):** the DALL-E tool message's raw prompt/JSON does NOT
   appear as message text in the export — only the image.

## 4. Failure handling (deliberate)

1. **Do:** open a Claude conversation with images, then log out of claude.ai
   in another tab (or drop network), then export from the still-open tab.
   **Expect:** export does NOT hang or throw; you get either a plain `.md`
   with italic `*[... not exported ...]*` notes (all assets failed) or a zip
   with the successful subset and a `, K failed` status. The conversation
   text is never lost.
2. **Do:** re-login and export again.
   **Expect:** clean zip again.

## 5. Edge cases

1. **Do:** export a conversation with two identically-named uploads
   (`photo.png` twice).
   **Expect:** `assets/photo.png` and `assets/photo-2.png`; both linked
   correctly from their own messages.
2. **Do:** export a very image-heavy conversation (10+ images, some large).
   **Expect:** completes (sequential downloads — allow ~1s per asset);
   status counts correct; zip opens in both Explorer and 7-Zip.
3. **Do:** popup filename field — clear it and type a custom name, export a
   media conversation.
   **Expect:** `<customname>.zip` containing `<customname>.md`.

## 6. HTML export (v1.5 primary deliverable)

> Why this exists: field testing showed normal users open exports in
> LibreOffice/Word/browsers, not markdown viewers — relative `assets/` links
> show as broken icons there. The `.html` export is ONE self-contained file
> with images embedded as base64 data URIs: double-click, opens in any
> browser, images inline at their exact conversation position, nothing to
> install, no assets folder. **Reviewer: open the .html in a BROWSER** —
> that is the target experience. (Word/LibreOffice can also open .html
> directly; worth one optional check, see step 6.)

1. **Do:** open the Claude conversation with images from section 2. Click
   the extension icon → the new **`.html`** button ("Opens anywhere").
   **Expect:** status progresses `Extracting… → Downloading N attachments… →
   preparing html… → Exported N messages + K images embedded from Claude`;
   ONE `.html` file downloads — no zip, no assets folder.
2. **Do:** double-click the downloaded `.html` (default browser).
   **Expect:** conversation renders with a title, a word-count line, clear
   alternating speaker labels (`[USER]` / `[ASSISTANT]` styles, matching the
   MD convention), and the images visible INLINE at their exact message
   positions. Hovering an image shows the position-encoded name
   (`msgNNN-imgN.ext`) as tooltip/alt.
3. **Do:** disconnect from the network, reopen the same `.html`.
   **Expect:** images still render — they are embedded, not fetched. Also
   view page source: image tags are `src="data:image/...;base64,..."`.
4. **Do:** export a **text-only** conversation as `.html` (any platform).
   **Expect:** one clean `.html`, same layout, no data URIs, no media status
   lines; a message containing literal `<script>` or `<b>` text shows it AS
   TEXT (escaped), never executes/renders it.
5. **Do:** if the conversation had a text attachment (.txt/.log) or a failed
   download, check its spot in the html.
   **Expect:** failed image → italic
   `[name -- not exported (download failed or unsupported)]`; non-image
   attachment → italic `[name -- attachment, not embeddable in HTML export]`.
   No literal `](asset:` anywhere in the file.
6. **Do (optional, the LibreOffice/Word case this feature fixes):** open the
   same `.html` in LibreOffice Writer or Word (File → Open).
   **Expect:** text and images appear inline — no broken-icon placeholders
   (this was the failure mode with the MD + assets zip).
7. **Size-guard note:** conversations whose embedded (base64) image payload
   would exceed **80 MB** fall back to the zip layout automatically — status
   says `Media too large to embed (~X MB > 80 MB cap) — exported zip with
   assets folder instead`, and the zip contains `<base>.html` whose images
   use relative `assets/` links (renders after extraction). Only testable
   with a deliberately huge conversation; skip unless one exists.
