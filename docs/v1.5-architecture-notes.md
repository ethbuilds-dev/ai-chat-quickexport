# v1.5 Media Export — Architecture Notes

Branch: `v1.5-media-export` (off `main` @ v1.4.3, commit aa5a722).
Status: draft for review. Nothing here is released or pushed.

## 1. How the extension works today (verified by reading the code)

### Active export path (the only one that runs)

```
popup.html / popup.js                    background.js (service worker)
 +----------------------+   message      +------------------------------+
 | detectPlatform(url)  | -------------> | onMessage CAPTURE_AND_FETCH  |
 | doExport(format)     | CAPTURE_AND_   |  captureTokenFromPage()      |
 |                      | FETCH          |  fetchConversation()         |
 | generateMD/JSON      | <------------- |   -> {title, messages[],     |
 | chrome.downloads     |  {data}        |       platform}              |
 +----------------------+                +------------------------------+
```

- **popup.js** detects the platform + conversation ID from the active tab URL,
  sends `CAPTURE_AND_FETCH` to the service worker, receives a *normalized*
  `{ title, messages: [{role, text}], platform }`, generates markdown or JSON
  **in the popup**, and downloads via `chrome.downloads.download()` with a
  blob URL created in the popup context.
- **background.js** owns all conversation fetching (per platform, below) and
  normalization to `{role, text}`.

### content.js is dead code (verified)

`manifest.json`'s `content_scripts` entry injects **only `styles.css`** — there
is no `"js"` array. `content.js` (the old in-page export button for ChatGPT)
is never loaded, and the message types it uses (`FETCH_CONVERSATION`,
`DOWNLOAD_FILE`, `AUTH_TOKEN`) have **no handler** in background.js.
v1.5 does not touch content.js; it stays as-is to keep the diff reviewable.

### Per-platform conversation fetch (verified from background.js)

| Platform | Where the fetch runs | Auth | Endpoint |
|---|---|---|---|
| ChatGPT | **Page MAIN world** via `chrome.scripting.executeScript({world:'MAIN'})` — the v1.4.3 fix; service-worker fetches get 403'd by Cloudflare bot management | Bearer token from `/api/auth/session` (re-acquired in-page) + cookies | `https://chatgpt.com/backend-api/conversation/{id}` |
| Claude | **Service worker** (works: no bot protection on claude.ai API) | Cookies (`credentials:'include'`), host permission `https://claude.ai/*` | `/api/organizations` then `/api/organizations/{org}/chat_conversations/{id}?rendering_mode=messages` |
| Gemini | DOM scrape via executeScript (no API) | n/a | n/a |
| Grok | Service worker | Cookies | `grok.com/rest/app-chat/...` |

### Where message content is transformed

- **background.js** normalizes raw platform JSON to `messages: [{role, text}]`:
  - Claude: `fetchClaude()` walks `conv.chat_messages[].content[]` blocks
    (text + thinking blocks). **Everything that is not text/thinking is
    dropped here** — this is where Claude images/files are currently lost.
  - ChatGPT: `walkChatGPTTree()` walks the `mapping` tree and keeps only
    `typeof part === 'string'` from `message.content.parts`. **Object parts
    (image asset pointers) are dropped here** — this is where ChatGPT images
    are currently lost.
- **popup.js** turns `messages` into the final `.md`/`.json` text
  (`generateMD` / `generateJSON`) and downloads a single file.

## 2. Where image/attachment references appear in each platform's JSON

### Evidence tiers used below

- **VERIFIED (code)** — provable from this repo's source.
- **OBSERVED (transcript)** — seen in a real local raw transcript of
  Claude-family message JSON that was available during development. That file
  turned out to be a *Claude Code session transcript*, *not* a claude.ai
  `chat_conversations` response — so it confirms the Anthropic content-block
  family (`{type:'image', source:{type:'base64', media_type, data}}` inside
  `message.content[]`), but **cannot** confirm claude.ai-web-specific fields.
  (Private file; schema learned from it, no content quoted anywhere.)
- **INFERRED** — based on the platforms' publicly known API shapes; not
  verifiable offline. Implemented defensively (feature-detect, log-and-skip).

### Claude (`chat_conversations` response)

VERIFIED (code): `fetchClaude` reads `conv.chat_messages[]`, each with
`sender` and `content[]` blocks of `{type:'text'|'thinking',...}`.

OBSERVED (transcript): Anthropic-format messages can carry image blocks
directly in `content[]`: `{ type:'image', source:{ type:'base64',
media_type:'image/png', data:'<base64>' } }`. v1.5 supports this shape as an
inline asset (no download needed). Whether claude.ai's web JSON ever uses it
is unconfirmed — but supporting it costs nothing and is grounded in real data.

INFERRED (needs one live conversation to confirm):

- `msg.files[]` / `msg.files_v2[]`: uploaded/pasted images, approximately
  `{ file_kind:'image', file_uuid, file_name, thumbnail_url, preview_url }`,
  `preview_url` being a same-origin path like
  `/api/organizations/{org}/files/{uuid}/preview`.
- `msg.attachments[]`: text-like uploads (pdf/txt/csv) carrying
  `{ file_name, file_type, file_size, extracted_content }` — extracted text
  inline in the JSON (no binary to download).

v1.5 scans **defensively**: `content[]` image blocks, `files`, `files_v2`,
`attachments`; anything exposing a URL-ish field (`preview_url`, `file_url`,
`url`, or one nested level under `document`/`image`/`file`/`asset`) or
`extracted_content`. Unknown shapes are logged
(`console.warn('[Exporter] media: ...')`) and skipped — never fatal.

### ChatGPT (`backend-api/conversation` response)

VERIFIED (code): `mapping[nodeId].message.content.parts[]` is a mixed array;
strings kept, objects dropped. The walker visits `role === 'user'`,
`'assistant'`, and (as of 2026-07-08) `'tool'` messages.

INFERRED (no ChatGPT fixture was available — all of this needs live
verification):

- Object parts with `content_type:'image_asset_pointer'` and
  `asset_pointer:'file-service://file-XXXX'` (newer conversations:
  `sediment://file_XXXX`). Also `size_bytes`, `width`, `height`.
- `message.metadata.attachments[]` as `{ id:'file-XXXX', name,
  mimeType/mime_type, size }` — used in v1.5 only to recover a human filename
  for the matching asset pointer.
- Download flow: `GET /backend-api/files/{file-id}/download` returning
  `{ status, download_url }`, where `download_url` is a signed URL on
  `*.oaiusercontent.com`. v1.5 also tries the alternate form
  `/backend-api/files/download/{file-id}` if the first fails.

#### ASSISTANT-GENERATED images (DALL-E) — the 2026-07-08 fix

BUG (real browser test, Zaina 2026-07-08): media export captured only
USER-uploaded images, never ASSISTANT-generated ones, in a ChatGPT image-gen
window with images on both sides.

VERIFIED (code): before the fix, `walkChatGPTTree` only processed
`role === 'user' || role === 'assistant'`. Any `role === 'tool'` message was
skipped entirely.

INFERRED (the root cause, needs live confirmation): in the ChatGPT DALL-E /
image-gen flow the generated image's `image_asset_pointer` does NOT sit in the
assistant text message's `parts[]`. It lives in a **separate message with
`author.role === 'tool'`** (typically `author.name` like `'dalle.text2im'`),
whose `content.parts[]` carries the pointer. Because the walker skipped tool
messages, generated images were silently dropped.

FIX (`walkChatGPTTree`, background.js): the walker now also scans `'tool'`
messages. From a tool message it collects ONLY image asset pointers (via the
same `MediaUtils.chatgptPartMedia`) and emits ONLY their placeholder(s) — the
tool message's string parts (prompt echoes, tool JSON) are dropped as
non-conversational. Each generated ref is tagged `generated:true` (so a
reviewer can tell uploads from generations) and its placeholder is attributed
to an `'assistant'` turn so it reads correctly in the transcript. Position
naming is unchanged: the popup derives `msgNNN-imgN` from the placeholder's
position in the message list, so a generated image gets the same treatment as
an upload. Defensive: a tool message with no recognizable image part emits
nothing (and, unlike unknown assistant/user parts, is NOT logged as "unknown"
— tool messages routinely carry non-media JSON, so logging would be noise).

Still INFERRED and needing one live image-gen conversation to confirm: that
generated images are on a `tool`-role message with an `image_asset_pointer`
part, and that the same `/backend-api/files/{id}/download` flow resolves the
generated file id (the download path is shared with uploads, so if uploads
download, generations should too).

## 3. v1.5 design

### Data flow

```
popup                background                    page MAIN world
  |  CAPTURE_AND_FETCH  |                              |
  |-------------------->| fetch + normalize            |
  |                     | + collect media refs         |
  |<--------------------| {title, messages, media[]}   |
  |  (media.length===0  |                              |
  |   -> EXACT v1.4.3   |                              |
  |      single-file    |                              |
  |      path)          |                              |
  |  FETCH_MEDIA        |                              |
  |-------------------->| inline base64: no fetch      |
  |                     | Claude URLs: SW fetch        |
  |                     | ChatGPT: executeScript MAIN -+-> /backend-api/files/{id}/download
  |                     |   -> download_url -> bytes   |   -> signed URL -> fetch bytes
  |<--------------------| {assets:[{id,name,base64}]}  |
  | rewrite placeholders|                              |
  | build zip           |                              |
  | chrome.downloads    |                              |
```

1. **Collection (background, during normalization).** Each detected
   image/file gets a media ref `{ id, alt, ... }` and a markdown placeholder
   appended to that message's text: `![<alt>](asset:<id>)` (no `!` for
   non-images). The response gains a `media` array **only when at least one
   ref was found** — a conversation without media produces exactly the same
   response object as v1.4.3.
2. **Download (background, on demand).** The popup sends `FETCH_MEDIA` only
   when `media.length > 0`. Inline refs (base64 image blocks, Claude
   `extracted_content`) need no network at all. Claude URL refs are fetched
   in the **service worker** with cookies — the same context that already
   fetches the conversation, proven to carry auth. ChatGPT assets follow the
   **v1.4.3 MAIN-world pattern**: the `/backend-api/files/.../download` call
   runs in the page (Cloudflare bot management), the resulting signed
   `oaiusercontent.com` URL is fetched in-page first (bytes base64'd there),
   with a service-worker fallback if the in-page fetch is CORS-blocked (new
   host permission `https://*.oaiusercontent.com/*` supports that fallback;
   host permissions bypass CORS in MV3).
3. **Bundle (popup).** Placeholder links are rewritten to `assets/<final
   filename>` (or an italic failure note if a download failed), then the
   export text plus each asset goes into one zip (`<base>.zip` containing
   `<base>.md` / `<base>.json` + `assets/...`), downloaded via the existing
   `chrome.downloads` call. If *every* asset download fails, the export falls
   back to the plain single file (with failure notes) rather than an empty
   zip.

### Why zip-in-popup with a small first-party zip writer (justification)

- **Why zip at all:** `chrome.downloads` fires one shelf entry per file; a
  30-image conversation as 31 separate downloads is hostile, and
  `filename:'folder/file'` subfolder downloads still spam the shelf and are
  fragile across Chrome download settings. One zip = one artifact, and
  relative `assets/...` links survive extraction. It also matches the
  existing architecture: the popup already owns "turn strings into a Blob and
  download it".
- **Why not JSZip:** vendoring ~100 KB of minified third-party code into a
  human-reviewed extension makes the diff unreviewable and bloats the store
  package. A STORE-only (no compression) zip writer is ~170 readable lines
  (`zipwriter.js`: local headers + central directory + CRC32),
  dependency-free, and unit-tested in Node including an independent reader
  round-trip and external validation via PowerShell/Python. STORE is the
  right choice anyway — PNG/JPEG/WebP don't recompress, and the markdown is
  tiny.
- **Why zip in the popup, not the service worker:** the popup already builds
  the final content and already calls `chrome.downloads` with a blob URL;
  `URL.createObjectURL` is unavailable in MV3 service workers, so building
  the zip where the download already happens is the minimal change.

### File layout: flat, matching the release packaging

Releases ship as a flat zip of root files (v1.4.3: 9 files — manifest,
background.js, content.js, popup.js, popup.html, styles.css, 3 icons). The
two new shipped modules therefore live at the **repo root** (`media-utils.js`,
`zipwriter.js`), not in a subfolder — release becomes an 11-flat-file zip
with no packaging-script changes. `tests/` and `docs/` are not shipped.

### Regression guarantee

The no-media path is preserved by construction, not by testing alone:

- background: media scanning only *adds* — placeholders and the `media` array
  appear only when refs are found; when none are found the returned object
  and every message text is identical to v1.4.3.
- popup: `if (!media.length)` short-circuits into the **verbatim v1.4.3
  code** (same generators, same filename logic, same `chrome.downloads`
  call). The zip branch is additive.
- Gemini is untouched (DOM scrape only, no JSON media path in this extension).
- Grok now has **defensive, inferred** generated-image detection (below); it
  is additive and byte-identical to before when no media is detected.

### Grok generated images (INFERRED, added 2026-07-08)

VERIFIED (code): `fetchGrok` normalizes from `responses[].message` (text) and
`responses[].sender`.

INFERRED (no Grok media sample was available — entirely guessed):
`MediaUtils.collectGrokResponseMedia(response, onSkip)` feature-detects a small
set of plausible image-URL shapes on a single response object:
`generatedImageUrls`/`imageUrls`/`image_urls` (url arrays);
`attachments`/`mediaAttachments`/`media`/`images` (arrays of
`{url|imageUrl|image_url|downloadUrl, fileName|name}`); and a single nested
`image`/`generatedImage` object. Each url becomes a
`{kind:'grok-url', url, name, isImage:true, generated:true}` ref, downloaded by
`fetchGrokAsset` (a plain cookie-authenticated SW fetch — grok.com runs no bot
protection; a CDN url ignores the cookies). Anything unrecognized returns `[]`
(with an `onSkip` log for media-ish-but-url-less entries) and never throws; a
thrown detector is caught in `fetchGrok` so a working text export is never
broken. **This may do nothing until a real Grok image conversation reveals the
true field names.**
