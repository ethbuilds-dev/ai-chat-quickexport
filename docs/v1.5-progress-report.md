## What is implemented

- **Detection** (`media-utils.js`, pure functions): Claude inline base64
  image blocks, Claude `files`/`files_v2`/`attachments` entries (URL-bearing
  or inline `extracted_content`), ChatGPT `asset_pointer` parts
  (`file-service://` and `sediment://`) with filename recovery from
  `metadata.attachments`. Unknown shapes are logged (`[Exporter] media:`
  prefix in the service-worker console) and skipped — never thrown.
- **Normalization hooks** (`background.js`): `fetchClaude`,
  `walkChatGPTTree`, and `fetchGrok` now emit `![alt](asset:<id>)`
  placeholders in the message text plus a `media` ref array — **only when at
  least one ref is found**; otherwise the response is exactly the v1.4.3
  object.
- **ASSISTANT-GENERATED images (2026-07-08 fix)**: the ChatGPT walker now
  also scans `role:'tool'` messages, where DALL-E puts generated images
  (`author.name` like `dalle.text2im`). Previously only `user`/`assistant`
  messages were walked, so generated images were dropped and only
  user-uploaded ones exported (Zaina's real-browser finding). Generated refs
  are tagged `generated:true`, emitted on an assistant turn, and get the same
  `msgNNN-imgN` position naming. Tool-message text chatter (prompt echoes,
  tool JSON) is NOT emitted. Grok also gained defensive, **inferred**
  generated-image detection (`collectGrokResponseMedia`), additive and a
  no-op when nothing matches. Gemini (DOM scrape, no JSON) is untouched;
  Claude assistant image blocks already flowed through the shared block path.
- **Download** (`background.js`, `FETCH_MEDIA` handler): inline text/base64
  need no network; Claude URLs are fetched in the service worker with
  cookies (the context already proven to carry claude.ai auth); ChatGPT
  files are resolved and fetched in the page MAIN world (reusing the v1.4.3
  Cloudflare fix), with a CORS-exempt service-worker fallback for the signed
  `*.oaiusercontent.com` URL (new host permission). Per-asset failures never
  fail the batch; downloads are sequential.
- **Bundling** (`popup.js` + `zipwriter.js`): asset filenames are
  sanitized/deduped, extensions fixed by magic-byte sniffing, placeholders
  rewritten to `assets/<file>` links, the normal generators run on the
  rewritten messages, and one `<base>.zip` (STORE, first-party ~170-line
  writer — see architecture notes for the JSZip justification) downloads via
  the existing `chrome.downloads` call. If every asset fails, or zipping
  fails, a plain single file exports with visible `*[... not exported ...]*`
  notes instead — text is never lost.
- **HTML export (the v1.5 primary deliverable, added 2026-07-08)**: a third
  popup button (`.html` / "Opens anywhere"). One self-contained file:
  `generateHTML()` (popup.js) renders semantic HTML with inline CSS —
  word-count header, alternating `[Label]` speaker markers matching the MD
  convention, line breaks preserved via `white-space: pre-wrap` — and every
  downloaded image embedded as a `data:MIME;base64,` URI at its exact
  placeholder position, with the position-encoded filename (`msgNNN-imgN`)
  as alt/title. All message text is HTML-escaped through
  `MediaUtils.escapeHtml` (script injection stays inert — tested). Failed
  downloads render as italic notes (same wording as `rewriteAssetLinks`);
  non-image attachments as italic "not embeddable" notes. Text-only
  conversations use the same generator (plain escaped text, no data URIs).
  **Size guard:** above 80 MB of embedded base64
  (`HTML_EMBED_CAP_BYTES`, popup.js) the export falls back to the zip
  layout — `<base>.html` with relative `assets/` links + the assets folder —
  with an explicit status message. Pure logic (`escapeHtml`, `mimeFromExt`,
  `convertPlaceholdersToHtml`) lives in `media-utils.js` and is covered
  offline. The md/json code paths are untouched.
- **Docs**: `docs/v1.5-architecture-notes.md` (pipeline + design +
  justifications), `docs/v1.5-MANUAL-TEST-PLAN.md` (click-by-click,
  including the new §6 HTML section).

## Known risks

1. **Field-name guesses (G1–G7)** — the design fails soft (log-and-skip,
   failure notes, plain-file fallback), so a wrong guess degrades to
   "images missing + console evidence", never to a broken export. Still:
   the feature may ship doing nothing until one live export tunes the names.
2. **Large conversations with many/huge images**: base64 assets travel
   through `chrome.runtime.sendMessage` (message-size limits on the order of
   tens of MB) and are concatenated in the popup. A 50 MB+ media set could
   fail the message or the popup allocation. Mitigation candidates if it
   bites: chunked transfer or per-asset messages. Not addressed in this
   draft.
3. **Popup lifetime**: closing the popup mid-download aborts the export
   (same as v1.4.3's fetch, but the media path takes longer). The status
   line shows progress; documented, not fixed.
4. **New host permission** (`*.oaiusercontent.com`) will trigger a Chrome
   Web Store re-review and a permission prompt for existing users on update.
   If undesirable, drop the SW fallback and rely on the in-page fetch (works
   iff the signed URL sends permissive CORS — unverified, G6).
5. **`preview` vs original for Claude** (G2) — could quietly export lossy
   images; explicitly step 2.5 in the manual plan.
6. **Filename edge**: popup `sanitize()` (pre-existing) plus zip-name rules;
   asset names are additionally sanitized/deduped and traversal-stripped in
   `media-utils.js`. Zip writer throws on duplicate names as a last line of
   defense (popup catches it and falls back to plain file).
